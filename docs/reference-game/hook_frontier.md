# H4 frontier from the DBSIM map

Generated by `tools/reference-game/scripts/hook_candidates.py --frontier` from the `map.json` of the current DBSIM map ([dbsim_map.md](dbsim_map.md)) against the registered hooks. The frontier is every live original function (entered in at least one suite, not a hook, not a runtime helper) with **two or more** live original callees left: the functions that the candidate lists of `hook_candidates.py` cannot admit. Counts are the saturated entry probes per suite (1000 = at least 1000).

A live callee is *replaced* when it is a hook or classified in-progress, *kept* when it is a runtime helper or classified H3, platform, RTL or dead in the verdict file (it stays original and is called as a guest), and *to do* otherwise. **To replace** is the function plus every to-do function reachable through to-do callees (functions / instructions, the members listed when there are at most four): what would have to be replaced bottom-up before the function itself is ready. **Height** is the longest chain of to-do callees below it (0 = every live callee is replaced or kept; recursion adds nothing). **Ready/one** counts the direct to-do callees that are ready themselves (no to-do callee) or have exactly one. **Kept** lists the guest calls that stay original in the subtree. "Live original callees" gives each callee's instruction count, or its verdict when it is kept. "Unprobed" lists callees without a probe row (liveness unknown, not counted; see the section of that name). "Hook links" counts hook callers / replaced callees.

**Ranking.** By class first, then by the size of the to-replace subtree (functions, then instructions; small first), then by the highest entry count (hot first). Classes: **A** replaced code still calls it (an adapter counts `call_<va>`; without `--bridge-calls`: a hook is a static caller); **B** calls a hook (replaced code sits below it); **C** reached from the logic frame or only through vtables/callbacks, no hook link; **D** reached only from the rendering, presentation or camera roots; **S** superseded: every static caller is a hook and no adapter counts a call to it, so it no longer runs in replaced mode (only with `--bridge-calls`). A and B are neighbours of replaced simulation code and the likeliest H4 targets; C holds the rest of the logic frame and the vtable/callback roots (HUD gadgets, cockpit, shell and simulation alike); D is rendering or presentation reach and normally H3; S comes last because the map counts were taken with every hook original and S functions are entered only from code that is replaced now (a pointer reference elsewhere in the image would still reach them, so check before calling one dead). Reach tags: L = logic frame `0x45f570` (through the map rows that list it as a caller), R = rendering `0x45fca8`, P = presentation `0x45fba4`, C = camera `0x4011a0`, V = none of them (vtable or callback only). Reach is static direct-call reach through map rows; functions that were already hooks when the map was taken have no row, so reach through them is missing. The class is a sorting aid, not a verdict: every role is a hypothesis until the contract is read from the bytes.

Verdicts from `docs/reference-game/function_verdicts.md`: frontier functions classified H3, platform, RTL, dead or in-progress are left out of the table and listed at the end; "Verdict" is H4 for a recorded H4 verdict and "open" for a function without one.

## Bridged-call inventory

Every hook that reaches original code through the guest bridge counts its
callees. The tables between the `bridge-table` markers are generated; the
text around them and the bridge notes are written by hand. The frontier mode
keeps the hand-written text from this heading on. Regenerate
the generated part after a regression run (frontier first, then the bridge
table into the frontier file):

```powershell
python tools\reference-game\scripts\hook_candidates.py `
    --bridge-table $env:ES2_DATA_REPO\logs\<run>\hook-counters.json `
    --bridge-calls tools\reference-game\proxy `
    --map <dbsim-map-dir>\map.json `
    --registry tools\reference-game\proxy\hook_registry.h `
    --classified docs\reference-game\function_verdicts.md `
    --bridge-notes docs\reference-game\hook_frontier.md `
    --image build\extracted\cd\VER95\DBSIM.EXE `
    --output docs\reference-game\hook_frontier.md
```

The script prints the original callees that have neither a note nor a
verdict; each gets a row in [function_verdicts.md](function_verdicts.md#verdicts), so
every original callee has a verdict.

**What is counted.** Every adapter keeps callee counters `call_<va>` (a
direct call of an original function) and `slot_<off>` (a virtual call
through vtable offset `<off>`), incremented only while the hook is
non-original; the tick log carries them as `hk_<hook>_call_<va>` and
`hk_<hook>_slot_<off>`. Most counters observe a real guest call through
the bridge (`weapons_guest_call` with the original's registers). A few are
counted without a game call because the core computes the callee itself
(kind **core** in the bridge notes, read from the adapter comments and
in `core/src`: the call site only calls the observer). Per suite
the `exit_counters` record is used where the runner wrote one, else the
last tick record. A callee that is a hook itself is fine: the bridge call
enters the nested hook, which keeps its own mode. Names come from the bridge
notes or from the first clause of the verdict reason in
[function_verdicts.md](function_verdicts.md).

**Counters without a call.** `shield` computes the balance step `0x413af8`
in core and only counts `call_413af8` (`shield_hooks.h`; `core/src/shield.c`
calls the observer only); its only callers are the two sites in
`shield_balance` (`0x413bfe`, `0x413c15`), so it is superseded. The same
holds for the two `sweep` hit-accumulator leaves. A hook registered after
the counter record has no `hk_*` counters and adds no caller rows; as a
callee it appears under "Callees that are hooks" with the counts of the run.

**Bridged originals that stay guest calls.** Each has a verdict row except the
15 marked "open" under "Original callees". One of them is H4: the command-key
callback `0x45a498` writes the queue that the command handler reads.

### Slot calls

A slot counter does not say which class received the call. For **actor**
receivers the slot matrix of
[vtables.md](../reverse-engineering/vtables.md#21-slot-matrix) settles it
for most slots: `+0x18`, `+0x20`, `+0x50`, `+0x74` and `+0x78` have a
hook in every concrete class (the `ACTOR` entries are the pure-virtual
trap, never reached), so every actor call through them enters a hook;
`+0x14` and `+0x1c` too, apart from the BASE family's trivial `0x411ab4`
and `0x406cfe`, whose only dispatch site is never reached. The other actor
slots end in small original leaves of `ACTOR`, `BASE` or `MECH` (getters,
empty bodies; `0x42200c` sets byte `+0xb1`). They are H4, too small for
a hook of their own: the hook that owns the calling site takes them, or
the caller computes them in core once the receiver's vtable is known.
The counted slots also reach non-actor classes: weapons (`fire_selected`,
`weapon_choose`, `group_fire`, `weapon_tally`, `aim_fire`: `+0x28` …
`+0x60`), shapes (`mech_aim_node`, `torso_aim`: `+0x20`, `+0x24`), gadgets
and HUD objects (`mouse_dispatch`, `player_input`, `cockpit_*`) and pool
objects (`removal_flush` `+0x08`: the destructors; `+0x10`, the
shape-word getter `0x46b910`). The receiver classes are in the histograms
below.
